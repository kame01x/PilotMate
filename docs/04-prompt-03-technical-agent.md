# Prompt 3 — Technical Agent

## Prompt to paste into opencode

```
This is Phase 3 of PilotMate: the Technical Agent. Read docs/01-architecture.md for full context before starting, and build on the existing backend/models.py, database, and agents/preflight_agent.py from Phases 1-2 — don't recreate the data model or duplicate shared setup (model client, .env loading, db session helpers). Factor out anything Phase 2 and Phase 3 both need into a shared module if it isn't already.

Build the Technical Agent in agents/technical_agent.py, with the following behavior:

1. CONVERSATION FLOW
   - The agent can be reached two ways: (a) via a button for a specific exercise type (e.g. stall, slow flight, landing) tied to the student's current or most recent Flight record, or (b) via free-form open-topic chat for any aviation theory question.
   - If reached via exercise type, the agent proactively presents: a short theory explanation, common student errors for that exercise, and a suggested reference (video and/or diagram) — then opens up for follow-up questions.
   - If reached via open topic, the agent answers directly and conversationally, asking a clarifying question only if the topic is genuinely ambiguous.
   - The student's authority (EASA / FAA / other, from their Student profile) matters for anything regulation-specific (airspace classes, minimums, procedures that differ by country). When an answer would differ by authority, the agent states which authority its answer assumes and flags that it may differ elsewhere — never presents one authority's rule as universal.

2. CONTENT SOURCES
   - Theory explanations: generated by the model directly (this is within its general aviation knowledge), not fetched from an external API.
   - Video references: implement a tool, e.g. find_reference_video(topic), that does a web search for a real, specific instructional video (prefer well-known flight-training channels/sources) and returns the actual link — never fabricate a URL. If no clearly relevant result is found, say so instead of guessing.
   - Diagrams: for exercises with a standard visual (e.g. traffic pattern, stall progression, slow flight attitude), describe the diagram in clear structured text (steps/stages) since this agent doesn't generate images in v1. Note in the output that a visual aid is recommended from the documentation library (Part 3) where available.
   - Common errors per exercise: model-generated from general flight-instruction knowledge, framed as "things students commonly get wrong," not as a diagnosis of this specific student (that's the Debrief Agent's job, later).

3. OUTPUT / LOGGING
   - Log each technical-coaching exchange (topic/exercise, key points covered, any flagged authority-specific caveat) to a simple conversation log tied to the student and, if available, the current Flight — structured so the future Debrief Agent can read "what was covered before this flight" without re-parsing raw chat text. Add whatever minimal model/table this requires to backend/models.py, consistent with the existing schema style, and explain the addition before making it.
   - Every regulation-specific or procedure-specific answer must state the assumed authority and include a one-line reminder to confirm against the student's actual POH/AIP/syllabus.

4. SAFETY AND VERIFICATION
   - Same human-in-the-loop principle as the Pre-flight Agent: the agent teaches and suggests, it does not assert itself as the final authority on procedure or regulation. No silent assumptions about which authority applies — use the student's profile, and say so explicitly in the response.

5. MODEL
   - Use the same Gemini model and .env pattern as Phase 2. If find_reference_video needs the same search tool/key as the Pre-flight Agent's NOTAM tool (e.g. Tavily), reuse that key — don't ask for a second one unless the tool genuinely requires different credentials.

Follow the rules in AGENTS.md. Explain any architectural decisions before making them, especially the new logging table and anything not explicitly covered above. After building, write a simple test script that simulates: (a) a student opening the Technical Agent for "stall" tied to an existing flight, and (b) the same student asking a free-form open-topic question that is regulation-specific (so we can see the authority-flagging behavior). Show me the output of both.
```

## What to check once opencode finishes

- For the exercise-type path: does it proactively give theory + common errors + a reference, without you having to ask for each piece separately?
- Does `find_reference_video` return a real, specific link — not a fabricated or generic one? If it can't find a good match, does it say so rather than guessing?
- For the regulation-specific open-topic question: does it explicitly state which authority (EASA/FAA/other) its answer assumes, based on the student's profile — not just silently pick one?
- Does it log the exchange in a way that's structured (not raw chat dump) and clearly tied to the student and flight?
- Did it explain the new logging table/model addition to you before building it, and does it fit the existing schema style in `backend/models.py`?

Once confirmed working, commit this checkpoint and move to **Prompt 4 — Debrief Agent** (the one that reads what the Technical Agent logged, and talks to the student after the flight).
