# PilotMate — Render Staging Deployment Guide

## Prerequisites

1. A [Render](https://render.com) account
2. A GitHub repository with the PilotMate code pushed
3. API keys for Groq, Gemini, Tavily (free tiers are sufficient for staging)

## Deployment Steps

### 1. Push to GitHub

```bash
git add .
git commit -m "Phase A+B+C: security fixes, user lifecycle, staging deployment config"
git push origin main
```

### 2. Create Render Blueprint

1. Go to Render Dashboard → **New** → **Blueprint**
2. Connect your GitHub repository
3. Render detects `render.yaml` and proposes three services:
   - `pilotmate-api-staging` (Python web service)
   - `pilotmate-frontend-staging` (Node web service)
   - `pilotmate-staging-db` (PostgreSQL)

### 3. Configure Environment Variables

After the blueprint creates the services, set these **manually** in the Render dashboard:

| Service | Variable | Value |
|---|---|---|
| pilotmate-api-staging | `GROQ_API_KEY` | Your Groq key |
| pilotmate-api-staging | `GEMINI_API_KEY` | Your Gemini key |
| pilotmate-api-staging | `TAVILY_API_KEY` | Your Tavily key |
| pilotmate-frontend-staging | `BACKEND_URL` | `https://pilotmate-api-staging.onrender.com` |

`JWT_SECRET_KEY` is auto-generated by Render. `DATABASE_URL` is auto-injected from the database service.

> **ALLOWED_ORIGINS:** leave it **unset**. The browser only talks to the frontend origin and reaches the API through the same-origin `/api-proxy` rewrite, so no cross-origin (CORS) requests occur. The backend defaults to an empty origin allowlist in staging, which blocks any accidental cross-origin browser access.

### 4. Run the Migration

After the database is provisioned, run the migration once.

**First, verify the database target.** The migration changes whatever database
`DATABASE_URL` points at. The target must be the Render staging PostgreSQL
database (`pilotmate_staging`), **not** your local SQLite file (`pilotmate.db`):

```bash
uv run python -c "from backend.config import DATABASE_URL as u; print('TARGET:', u.rsplit('@',1)[-1] if '@' in u else u)"
```

- Correct: `TARGET: <render-host>:5432/pilotmate_staging` → proceed.
- Wrong: `TARGET: sqlite:///./pilotmate.db` → **stop** — you are pointed at the
  local development database. In the Render shell `DATABASE_URL` is injected
  automatically; running locally you must pass it explicitly (see below).

Then run the migration:

```bash
# On Render shell (DATABASE_URL auto-injected) or locally against the staging DB:
DATABASE_URL="postgresql://..." uv run python scripts/migrate.py
```

Or add a one-off job in Render:
- Type: **Cron Job**
- Schedule: `0 0 30 2 *` (Feb 30 = never runs automatically)
- Command:

  ```bash
  uv run python -c "from backend.config import DATABASE_URL as u; print('TARGET:', u.rsplit('@',1)[-1] if '@' in u else u)" && uv run python scripts/migrate.py
  ```

  (prints the target in the job log before migrating, so a wrong target is visible)
- Environment: add `DATABASE_URL` → **From Database** → `pilotmate-staging-db`
  (`connectionString`). **This binding is required** — a cron job without it
  falls back to local SQLite and silently does nothing to staging.

### 5. Create the Admin Account

Verify the target again first with the same command as step 4 —
`create_admin.py` writes to whichever database `DATABASE_URL` points at, and it
must be the Render staging PostgreSQL database (`pilotmate_staging`), not local
SQLite:

```bash
uv run python -c "from backend.config import DATABASE_URL as u; print('TARGET:', u.rsplit('@',1)[-1] if '@' in u else u)"
```

Then create the admin:

```bash
DATABASE_URL="postgresql://..." uv run python scripts/create_admin.py
```

Enter the admin email, name, and password when prompted.

### 6. Restrict Staging Access

Staging is protected by an HTTP Basic Auth gate in `frontend/src/proxy.ts`. Set these environment variables on the frontend Render service:

| Variable | Description |
|---|---|
| `STAGING_AUTH_USER` | Basic Auth username |
| `STAGING_AUTH_PASS` | Basic Auth password (use a strong secret) |

If either variable is missing on Render (`RENDER=true`), the frontend responds 503 rather than exposing the site. Local development is unaffected — the gate only activates when credentials are set.

Additional options:

**Option A — IP allowlist (Render dashboard):**
- Frontend service → Settings → IP Allow List → Add your IP

**Option B — Cloudflare Access (recommended for testers):**
- Put the frontend behind Cloudflare Access with an email allowlist

> **Note:** Render's free tier does **not** include built-in web-service authentication. Do not rely on it. Use the `STAGING_AUTH_USER`/`STAGING_AUTH_PASS` gate above.

### 7. Verify Deployment

Run these checks against the staging URL:

```bash
# Health check
curl https://pilotmate-api-staging.onrender.com/health

# Public signup blocked
curl -X POST https://pilotmate-api-staging.onrender.com/auth/student/signup \
  -H "Content-Type: application/json" \
  -d '{"name":"test","email":"test@example.com","password":"password123"}'
# Should return 422 (missing invite_code)
```

Then log in as admin and test:
- Create an invite via `POST /admin/invites`
- Sign up with the invite code
- Approve the pending account
- Verify login works
- Test aircraft ownership, pre-flight, mass & balance, messaging

## Environment Summary

| Environment | Frontend | Backend | Database |
|---|---|---|---|
| Local dev | `localhost:3000` | `localhost:8000` | SQLite (`pilotmate.db`) |
| Staging | `pilotmate-frontend-staging.onrender.com` | `pilotmate-api-staging.onrender.com` | Render PostgreSQL |

## Rollback

Render keeps the last 10 deploys. To roll back:
1. Go to the service → **Deploys**
2. Find the last working deploy
3. Click **Rollback**

## Backups

Render PostgreSQL includes automated daily backups (7-day retention on paid plans, 1-day on free). For additional backups, use `pg_dump` via a cron job.
